## Status
- Prepared from `main` commit `b079e953a4198123b21b6f706f7bfa9ca9fec097`.
- The CAS schema/functions are installed in Supabase project `myuwytzbkckemcyfvhkx` through migrations `agenda_items_cas_sync_path`, `agenda_legacy_migration_no_stale_resurrection`, `agenda_items_service_role_cas_only`, and `agenda_cas_reject_null_type`.
- `agenda_sync_control.enabled` is intentionally `false`. This branch's new app path is dormant until the server-side cutover is explicitly enabled.
- No `kv` policy has yet been changed; legacy clients remain unaffected. No app code has been merged to `main` or published. The new app detects cached legacy-list divergence from normalized rows, keeps the local item state, and pauses those items for an explicit per-item resolution rather than overwriting either side.

## Data contract
- App reads `agenda_items` per event/task and keeps `kv` for every other legacy app key.
- App changes are sent one item at a time to `agenda_item_cas`, with the item ID, optional expected version, and tombstone delete flag. Creation only succeeds when the item is absent; updates/deletes only succeed at the exact expected version. Stale writes return `conflict` and preserve local pending data rather than retrying over newer server data.
- An offline per-item queue and its base versions are stored locally. On reconnect it retries with that same base version; the server reports a conflict rather than silently rebasing stale edits.
- The one-time legacy importer reads `agendaplus_events` / `agendaplus_tasks` from `kv` only for a user whose normalized table has no rows. It uses insert-if-absent, never overwrites normalized rows. Existing normalized users are marked migrated without merging the legacy snapshot, avoiding stale-list resurrection. Existing `kv` rows are retained.
- Authenticated and service roles can select normalized agenda rows but cannot write directly; all writes must use the CAS RPC. RPCs are `SECURITY DEFINER` with empty `search_path`, require `auth.uid()`, and are executable only by `authenticated`.

## Cutover blocker / risks
Old app builds continue whole-array writes to `kv`. The new app must not merge those arrays after normalized data exists. Enabling the flag alone is therefore not a complete rollout: stale app builds could keep changing legacy `kv` while new builds only read normalized rows, and the two sources would diverge. A controlled follow-up must deploy the app first, then apply a version barrier that prevents legacy `agendaplus_events` / `agendaplus_tasks` writes, and only then set `agenda_sync_control.enabled=true`. Old builds would no longer sync those two arrays; their on-device data remains but those builds need an explicit upgrade notice/support plan. Do not enable the flag until the barrier and user-facing path are reviewed and an authenticated CAS integration test is available.

The current rollout intentionally does not alter the existing `kv` policy or enable the new path. The branch adds a basic per-item conflict-resolution choice (`Manter local` / `Usar nuvem`); it is not yet exercised with authenticated clients and needs product review. Choosing `Manter local` explicitly authorizes a CAS write against the displayed server version; a subsequent race still returns a conflict. Offline startup still depends on the existing auth/session flow.

## Scheduler compatibility stage

Production inspection on 2026-11-27 found deployed Edge Function `scheduler` version 2 (`verify_jwt=false`, SHA-256 `b64cd987cc6342fab7789ca9f617114c17c8a9ad36ea49dd22eaed244d7fefad`). Its source authenticates requests with `x-cron-key`, loads each user’s complete `kv` object, and derives events/tasks from `agendaplus_events` / `agendaplus_tasks`; it does not read `agenda_sync_control` or `agenda_items`. The service-role client bypasses RLS, so all user-specific reads must include an explicit `user_id` predicate.

A replacement candidate is staged at `supabase/functions/scheduler/index.ts` but is NOT deployed. It reads `agenda_sync_control.enabled`; false preserves legacy schedule reads; true reads `agenda_items` with an explicit `user_id = uid` filter, ignores versioned `_deleted` tombstones, and continues reading birthdays only from that same user’s `kv` row. Flag read failures fail closed (HTTP 500), rather than silently falling back to stale arrays. The endpoint keeps the existing cron-key check and never returns the service-role key. Before deployment, compare its behavior to version 2, run Deno type/lint checks, and verify scheduled dry runs without sending pushes.

## Legacy writer barrier and cutover safety

The staged candidate `supabase/migrations/20261127123500_agenda_legacy_kv_write_barrier.sql` replaces the existing broad `own kv` policy with owner-scoped SELECT and INSERT/UPDATE/DELETE policies. The two legacy agenda keys remain readable; their writes are denied only when `agenda_sync_enabled()` returns true, while other `kv` keys retain existing owner writes. This relies on the existing flag RPC (`SECURITY DEFINER`, empty `search_path`, authenticated-only EXECUTE). The migration has NOT been applied: production `kv` RLS and all legacy data remain unchanged.

The feature flag transition provides the actual version barrier: after it is enabled, stale builds cannot commit whole-array event/task writes; they may read the old arrays, but new builds use versioned CAS. This blocks post-cutover resurrection/loss from stale clients. It does NOT resolve legitimate legacy edits made after the original normalized backfill but before cutover. Because the importer intentionally skips legacy lists for users who already have normalized rows, a read-only reconciliation/diff of `kv` arrays versus normalized items is a required precondition; ambiguous differences must be reviewed/resolved before enabling. The app currently detects differences on the device’s local cache, not by reconciling the server’s `kv` arrays, so that alone is not sufficient. A rollout also needs a user-facing upgrade path for old builds that receive RLS errors on those two keys.

Recommended order is: reconcile cloud `kv` versus normalized rows without mutation; publish the app with CAS path dormant; complete authenticated two-account isolation/CAS tests and stale-client failure tests; compare/deploy the scheduler candidate while the flag is still false (so it retains v2's legacy read path), and verify dry runs with no push; apply and verify the barrier migration while the flag is false; then, only after explicit approval, atomically quiesce `kv`, re-run reconciliation, and enable the flag. Do not enable before deploying the candidate scheduler: v2 reads only legacy arrays and would become stale as soon as CAS writes begin. A production read-only reconciliation was run on 2026-11-27 using `tests/sql/agenda_reconciliation_dry_run.sql`. It found one user with arrays and normalized rows: events 10/10 and tasks 5/5; zero malformed values/entries, duplicate legacy IDs, or differing IDs/fields. The sorted per-type checksums match exactly (events `a5cc73ef655143185b0a75580bcdcdad`; tasks `ff3409ea3140861e7220134180b5b3cc`). The report did not fetch or return titles/descriptions/payload values. This is a point-in-time result, not proof that the arrays did not change after the query; rerun under write quiescence immediately before enable. The read-only query is added to `tests/sql/agenda_reconciliation_dry_run.sql` and covered by a static no-DML contract test.

The stage still stops before the RLS migration or flag change because authenticated integration tests and the old-client recovery path are not available here. A cutover must re-run the report under an admin transaction that first locks `public.kv` in `SHARE ROW EXCLUSIVE` mode, then reconcile any newly divergent rows only from owner-approved per-item decisions with exact expected versions; abort if anything remains unresolved, set the flag true only in that same transaction, and commit. Never infer a winner from timestamps, counts, or hashes. Old app versions bulk-upsert multiple `agendaplus_*` keys: a rejected agenda item can fail the entire batch and prevent unrelated settings from syncing, so explicitly test and communicate that compatibility impact before enable. No reconciliation DML, policy change, flag change, app release, merge, or Edge Function deployment was made.

### Old-client/version barrier investigation (2026-11-27)

The staged branch has no app/build version identifier or mandatory remote preflight that old clients call. `sw.js` installs with `skipWaiting()` and claims clients, but has no `fetch` handler or Cache Storage use; the app registers it only on the push-notification path. Thus the worker does not serve or replace cached app assets, and `skipWaiting()` cannot replace JavaScript already executing in an open tab. A client must reload/fetch the page before it can run the new code. The currently served GitHub Pages `index.html` and `sw.js` respond with `Cache-Control: max-age=600`; this is a short edge/browser cache window, not a version barrier. The staging branch's `index.html`, `sw.js`, and `manifest.json` match the fetched remote branch at commit `1b1647bfb7ca390b3e340692adc6b3dff895ab23`.

A preflight gate added only to the new app can warn or block that new app, but cannot stop an old tab/build from issuing its legacy multi-key upsert. The staged RLS barrier remains the authoritative protection against old array writes once enabled; under PostgREST's transaction semantics a rejected agenda row also rejects unrelated rows in that same request. The barrier therefore prevents a stale write to the legacy schedule from becoming authoritative but does not provide old-build upgrade UX or preserve unrelated settings in that failed batch. Local browser storage is not erased by the failed request itself, but it is not a portable or verified backup and must not be represented as one.

No client-side/server-side change is safe to claim as a complete old-build solution before a product choice and authenticated staging test. Options for the owner: (1) defer the barrier/flag until accepting a deliberate old-build cutoff is possible; (2) approve a communicated cutoff, require users to reload/use the new build, and explicitly accept that still-running legacy builds may fail whole-batch cloud sync while retaining local data, with a tested recovery path; or (3) first ship and test a compatibility release that splits non-agenda writes and provides upgrade/recovery messaging, while recognizing that users still running earlier JavaScript cannot be forced into it by the current service worker. The safest immediate action is to leave the flag off and do not apply the barrier until one option is chosen and the stale-client batch-failure/recovery flow is verified in disposable authenticated staging. Do not infer from the service worker that old tabs will update on their own.


## Security review

Supabase’s 2026-11-27 security advisor reported the expected generic `authenticated_security_definer_function_executable` warning for `agenda_item_cas`, `agenda_migrate_legacy_items`, and `agenda_sync_enabled` (also for unrelated `delete_my_account` and `notify_inbox`). The relevant agenda functions authenticate with `auth.uid()`, use `SET search_path = ''`, fully qualify table references, and scope agenda reads/writes to the calling UID. Direct `agenda_items` writes are revoked from both `authenticated` and `service_role`; the CAS RPC is granted only to `authenticated`. The linter warning is still a real review surface: any bug in a definer RPC runs with its owner’s privileges. Accepted mitigation is to keep the narrow API surface, revoke `PUBLIC`/`anon`/`service_role` EXECUTE, reject null UID and malformed IDs/payloads, retain exact-version checks and tombstones, and continue auditing definitions/ACLs. Do not silence the warning by switching the CAS boundary to invoker while direct table writes remain revoked. Remediation guidance: https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable.

The advisor also reports five RLS-enabled/no-policy INFO findings (`agenda_item_migrations`, `agenda_sync_control`, `app_secrets`, `push_log`, `week_state`); these tables are intentionally not client-accessible and have no authenticated policies, but confirm privileges remain revoked and service role is the only intended operational access. It reports one separate `anon_security_definer_function_executable` warning for `notify_inbox()`; that is outside this agenda task and was not changed. It also reports leaked-password protection disabled, an Auth setting not changed here.

### Compatibility build stage (2026-11-27)

This staging-only revision adds a client compatibility path; it does not enable the flag, apply the RLS barrier, publish Pages, merge to `main`, or deploy any server code.

- With the flag explicitly false, the app continues legacy `kv` agenda sync. If a mixed agenda/settings upsert is denied with SQLSTATE `42501` or a recognizable RLS/permission error, it retries only non-agenda preference rows, leaves event/task data in local storage, and shows a Portuguese recovery notice. Generic failures retain the local retry queue; they are not mislabeled as an agenda cutoff.
- With the flag true, event/task arrays are excluded from every `kv` write path (automatic flush, manual sync, bootstrap seed, and logout); event/task sync uses the CAS channel, while other `agendaplus_*` settings continue through `kv` independently. The app does not call the legacy-to-normalized importer automatically. If normalized agenda rows are absent, it preserves local/legacy arrays and shows a notice instead of importing them or overwriting them with an empty list. Per-item differences against normalized rows remain explicit conflicts.
- If offline or unable to confirm the feature flag, bootstrap still opens the app using local data; preference reads/writes are isolated, agenda arrays are not pushed, and local queued writes are retried when connectivity returns. Logout is blocked when it cannot confirm that agenda changes reached cloud; it does not clear local agenda data in that case.
- The `42501` classification is intentionally conservative but covers permission errors beyond the barrier. The user-facing recovery notice is therefore triggered only when the rejected batch actually contained `agendaplus_events` or `agendaplus_tasks`; non-agenda-only permission errors remain ordinary sync errors.

This compatibility release cannot notify or split writes for JavaScript already executing in an older tab/build. Those clients continue their original mixed bulk-upsert behavior until they reload/fetch the new app; GitHub Pages has a short cache window but no enforceable minimum-build preflight or fetch-intercepting service worker. Do not treat this as a forced upgrade or as approval to apply the barrier/enable the flag. Keep both server-side rollout controls dormant pending the user's cutoff choice and authenticated tests.

Remaining checks before any release/cutover: run the staged build with authenticated test accounts in a disposable environment; verify legacy-off, flag-on, denied mixed batch, offline/reconnect, CAS conflict, and logout behavior in real browser flows; visually review the new Portuguese notice. No authenticated/visual test was performed in this staged build task. Existing already-open tabs remain a limitation until they reload/cache expires.

### Staging-only MCP agenda candidate (2026-11-27)

`supabase/functions/tnc-mcp/index.ts` on this branch adds `listar_itens_agenda`, `criar_item_agenda`, `atualizar_item_agenda`, and `cancelar_item_agenda` alongside the existing connection check. This is source-only staging work; the production `tnc-mcp` Edge Function remains unchanged and has not been deployed.

- Every request uses `withSupabase({ auth: 'user' })`, resolves the caller through `supabase.auth.getUser()`, and uses no service-role key. List and update reads add an explicit `user_id = auth.uid()` predicate (plus item-type/item-id constraints); RLS remains an additional boundary.
- Listing pages at most 100 rows, returns only an allowlisted event/task payload shape, and omits `_deleted` tombstones. Event/task payload fields are validated separately; unknown JSON keys are stripped from database output and rejected from create/update inputs. IDs, dates, times, text, numeric fields, and bounded tag/dependency/subtask arrays have explicit validation limits. Inputs never accept `user_id`.
- Creation requires a caller-provided app item ID and calls `agenda_item_cas` with a null expected version; the RPC inserts at version 1 only if the key is absent, otherwise returning conflict without overwrite. Update reads the current row, merges only validated fields, requires the caller's exact `expected_version`, and calls the CAS RPC. Cancellation calls the same RPC with `p_is_delete=true`; this is a versioned `{"_deleted":true}` tombstone, not a physical delete. CAS conflicts are returned as conflicts without automatic retry/rebase.
- The MCP handler validates the SDK's JSONB result whether decoded as an object or JSON text, checks the status/version contract, and serializes only whitelisted payload fields. Tool descriptions say writes are immediate, require explicit user intent, and can conflict.
- `agenda_sync_enabled()` is checked before writes. While the global flag remains false, create/update/cancel return `agenda_sync_disabled` and do not call the mutating RPC. No flag or barrier was changed. If the flag is later enabled, authenticated MCP writes will still require end-to-end validation before release.

Read-only production catalog review on 2026-11-27 confirmed the applied signature `agenda_item_cas(text,text,jsonb,bigint,boolean) RETURNS jsonb`; creation is `p_expected_version = NULL`/version 1 insert-if-absent; updates/deletes require exact version; delete payload is a tombstone; statuses are `applied`, `conflict` (with current version/payload), or `not_found`. `agenda_sync_enabled()` returns the global flag. The reviewed agenda RPC definitions are `SECURITY DEFINER`, set empty `search_path`, reject missing `auth.uid()`, and fully qualify `public` objects. Catalog ACLs showed EXECUTE only for the function owner and `authenticated` (no PUBLIC/anon/service_role), matching the staged migration's narrow grant. Direct table writes remain revoked; `agenda_item_cas` is the sole mutation path.
